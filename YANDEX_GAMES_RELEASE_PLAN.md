Реализовано:

- `YandexAdapter.showRewardedAd()` вызывает официальный `showRewardedVideo`. Две точки: `battle-gold-double` и `battle-speed-double`; автоматических interstitial нет. Один активный рекламный запрос, награда только по `onRewarded`, защита от дублей/поздних событий и сохранение независимых источников паузы. Рекламного watchdog, снимающего паузу поверх ролика, нет.
- Золото: добавляется зафиксированное `BattleReport.goldEarned` в кошелёк исходной эпохи; дельта и receipt записываются вместе. До записи сохраняется подтверждение для восстановления. Если запись не удалась, кнопка повторяет сохранение без новой рекламы. Если все записи заблокированы, подтверждение остаётся только в памяти до закрытия вкладки. Последние 128 receipts ограничивают размер профиля; предложения закрытых попыток больше недоступны.
- Скорость: право и выбранный ×1/×2 привязаны к уникальной попытке, сохраняются в походе и восстанавливаются при перезагрузке. Повтор через UI открывает подготовку с новой попыткой. Новый этап/поход сбрасывает право. Базовые формулы не умножаются; визуальные эффекты следуют скорости симуляции. Debug-множитель независим и отсутствует в режиме `yandex`.
- Результат сохраняется отдельно от похода, включая финальную победу и поражение. Возвращение к нему доступно из меню исходной эпохи; повтор callback или восстановление не начисляет второй бонус.
- `CloudProfileStorage`: полный снимок профиля, изоляция аккаунтов, однократный перенос старого локального прогресса в первый аккаунт. При конфликте — выбор одного снимка, без суммирования золота/талантов; обе версии сохраняются локально для восстановления. Новый облачный профиль загружается до создания `GameDirector` и Game Ready. Debug исключён из синхронизации.
- Запись `setData(..., true)` не чаще раза в 5 секунд, после проверки текущей облачной версии. Изменения сразу сохраняются локально, ошибки оставляют очередь. Данные ограничены запасом 190 КБ относительно лимита SDK 200 КБ. Если другой клиент изменил облако, отправка останавливается до перезагрузки и выбора профиля. SDK не предоставляет compare-and-swap: одновременные записи двух устройств не дают гарантии серверной транзакции.
- `npm run package:yandex` собирает отдельный `dist-yandex/`, проверяет пути, ресурсы входной страницы и предел 100 000 000 байт, создаёт ZIP с `index.html` в корне. Обычная production-сборка сохраняет прежние инструменты разработки.

Для черновика включить облачные сохранения, монетизацию и русский язык; стики-баннеры выключить. Поддержку устройств заявлять по фактической приёмке, ТВ пока не заявлять. Договор, права на материалы, рейтинг, карточка и промоматериалы оформляются в Консоли владельца.

Перед модерацией остаётся приёмка настоящего SDK, рекламы, профилей и материалов; физические устройства приняты по апруву пользователя. Во встроенном браузере текущая релизная сборка загрузила меню, а геометрия поля измерена на четырёх размерах. Полный игровой путь и платформенный черновик ещё не проверены. ### Обнаруженные проблемы и порядок устранения

1. **П, 3.4.5:** `src/data/content.ts` содержит «Монах лекарь» и упоминание монаха в финале шестой эпохи. На контактном листе у персонажа книга с крестом и монашеское облачение. Для выпуска нужен светский образ лекаря, нейтральное название и проверка обоих цветов, всех кадров и карточек. Уже принятые модели в этом аудите не переделаны: правило проекта запрещает такой пересмотр без запроса пользователя.
2. **П/риск, 3.4.4:** название девятой эпохи «Мировые войны» явно отсылает к историческим войнам. Стилизованная графика не исключает риск. Нужны согласованный вымышленный сеттинг и аудит символики/названий либо письменное разъяснение модерации по конкретному набору изображений. Предсказать решение модерации нельзя.
3. **П по исходной геометрии, 1.6.2.2:** `.game-shell` и `.arena` в `src/ui/fullscreen.css` занимают весь viewport, ограничения пропорций нет. Для контрольного ПК-размера 1911×940 отношение равно 2,033; для 2560×1080 — 2,370. Ограничить активное поле на широких desktop-экранах, сохранив касание одного края по 1.6.2.1; затем проверить DOM и видимые кнопки. Подтверждение фактических границ поля в браузере пока открыто.
4. **П по порядку вызовов, 1.19.2:** `mountGame` создаёт интерактивный `GameUI` и обработчики до окончания preload; `BattleScene.create` вызывает ready позднее. Диалог `chooseCloudProfile` также интерактивен до ready. Устранить разрыв между первой доступной интеракцией и ready: заблокировать/скрыть интерфейс до готовности ресурсов, либо корректно отметить ранний доступный интерфейс. Зафиксировать время, стоимость улучшений, число поражений и понятность подсказок; оценить управление одной рукой на телефоне. Само наличие 40 боёв не доказывает комфортное прохождение.

**G. После публикации и итог модерации.** Рейтинг и решение модератора до выпуска отсутствуют. После допуска контролировать карточку и замечания сервиса, рейтинг и жалобы/ошибки. Успех локальных тестов не гарантирует решение модерации; открытые проверки закрываются журналом конкретной версии ZIP и устройства, а не общей отметкой «всё соответствует».

## 2. Где размещать игру и сколько она должна весить

### Основной способ: хостинг Яндекса

Загружаем ZIP через [Консоль разработчика](https://games.yandex.ru/console/). Файлы размещает Яндекс; игроки открывают игру в каталоге. GitHub хранит исходники, `dist/` служит результатом сборки, ZIP — загружаемым артефактом. Это три разных объекта.

**Ограничение: до 100 МБ всех файлов после распаковки.** Маленький ZIP не спасает слишком большую распакованную сборку. В архиве должен быть `index.html` непосредственно в корне; имена файлов/папок — без пробелов и кириллицы. Один архив содержит все поддерживаемые устройства и языки. [Загрузка игры](https://yandex.ru/dev/games/doc/ru/console/add-new-game).

Правильная структура:

```text
znamyona-epoh-1.0.0.zip
├── index.html
└── assets/
    ├── game-....js
    ├── game-....css
    ├── stone-u-...-sheet.png
    ├── bronze-u-...-sheet.png
    ├── arena-stone.svg
    └── audio/
        ├── arena-theme.ogg
        └── arena-theme.mp3
```

Неправильно: `archive.zip → dist/ → index.html`. Архивировать нужно **содержимое** `dist/`, а не внешнюю папку.

Текущие 8,413 МБ включают лабораторию и вспомогательные ресурсы. Они сохранены по указанию пользователя; подготовка публичного состава отложена. ZIP ещё не является проверенным релизным архивом; его размер нужно измерить отдельно после доработок.

Наш внутренний запас: держать сборку существенно ниже 100 МБ, а проверку размера строить по консервативному пределу 100 000 000 байт. Рабочая цель первого релиза — остаться около текущего объёма; это цель проекта, не дополнительное правило платформы.

Размер на диске не равен расходу памяти. Большие атласы после декодирования могут занимать значительно больше; проверять слабые телефоны необходимо даже при небольшом архиве.

### Когда нужен свой хостинг

Внешнее размещение через iframe согласовывают с поддержкой: передают название, аккаунт, HTTPS-ссылку и объяснение, почему ZIP не подходит. Это вариант для сложной серверной архитектуры. У нашей игры такой причины сейчас нет. [Загрузка игры](https://yandex.ru/dev/games/doc/ru/console/add-new-game).

При дальнейшем добавлении серверных возможностей пересмотреть архитектуру отдельно. Сама облачная запись через SDK не требует нашего сервера.

## 3. Аккаунт, договор и монетизация

1. Создать или использовать полноценный Яндекс ID с логином Яндекса. Упрощённый аккаунт только с внешней почтой может мешать подключению монетизации.

Часовой пояс рабочего компьютера не определяет юридический статус владельца. Возможность договора и выплат для конкретной страны/банка нужно подтвердить в собственном профиле и при необходимости в поддержке **до вложений в релиз**. Не подставлять российские реквизиты и статус автоматически.

Первый релиз — две добровольные рекламные точки: **золото за завершённый бой ×2** на экране результата и **темп всего предстоящего боя ×2** на подготовке. Подробная спецификация — в разделе 4.5, уточнена по предложению пользователя 28.09.2026. Автоматические межбоевые показы предлагается не включать в первую версию этой схемы. Платных товаров нет. Золото за убийства/время/победы и покупка талантов за заработанное золото сами по себе не являются платежами реальными деньгами.

Если позднее появятся платные товары, понадобится отдельная интеграция платежей, выдачи/восстановления/консумирования и облачного прогресса. Не включать покупки в карточке до появления этой реализации. Подробности: [SDK покупок](https://yandex.ru/dev/games/doc/ru/sdk/sdk-purchases).

Для ЕЛС документация описывает выплату при достижении порога в течение 20 рабочих дней следующего месяца; актуальный порог определяется условиями партнёра. Не считать доход гарантированным и не использовать рекламные обещания заработка как бюджет проекта. [Выплаты](https://yandex.ru/dev/games/doc/ru/payments).

## 4. Доработки SDK и игры

### 4.1. Подключить SDK, а не ждать его появления

Файлы: `index.html`, `src/main.ts`, `src/platform/yandex.ts`.

Для ZIP на сервере Яндекса официальный путь — **`/sdk.js`**. Его не скачивают в архив. Загрузить скрипт, дождаться его загрузки, затем выполнить `YaGames.init()`. При асинхронном подключении обязательно устранить гонку с запуском приложения. [Подключение SDK](https://yandex.ru/dev/games/doc/ru/sdk/sdk-about).

```html
<!-- Пример подключения на хостинге Яндекса -->
<script src="/sdk.js"></script>
```

Исправлено: production-адаптер динамически загружает `/sdk.js`, ожидает загрузку и выполняет init; уже подключённый SDK использует сразу. Ошибка даёт локальный fallback. Облачная загрузка профиля подключена 30 сентября. Структура запуска:

```text
загрузить SDK → init → определить язык → загрузить/согласовать профиль
→ подготовить UI и необходимые ресурсы → Game Ready
```

Локальная разработка должна сохранять отдельный fallback. Для тестов SDK использовать официальное тестовое окружение/проксирование `/sdk.js` или черновик. Успешный fallback на localhost не доказывает интеграцию в Яндексе.

### 4.2. Передать реальную готовность

Реализован `ysdk.features.LoadingAPI.ready()` после готовности сцены и SDK, однократно; при ошибке загрузки ресурсов сигнал не отправляется. Проверено с моками. Требование: сигнал после фактической готовности интерфейса и необходимых игровых ресурсов. `mountGame()` создаёт Phaser асинхронно, поэтому возврат из функции ещё не является доказательством загрузки сцены. Нужен сигнал из жизненного цикла сцены плюс готовность стартового экрана. [Game Ready](https://yandex.ru/dev/games/doc/ru/sdk/sdk-game-events).

Не привязывать готовность к произвольному таймеру или первому клику. При нынешней предварительной загрузке обеих эпох ориентироваться на завершение загрузки сцены. При будущей ленивой загрузке отдельно определить, какие ресурсы нужны для первого доступного взаимодействия.

Критерий: зелёный индикатор появляется одновременно с доступной игрой; официальный тест ожидает это в пределах 90 секунд, но 90 секунд — край проверки, не целевая скорость загрузки. [Методика SDK](https://yandex.ru/dev/games/doc/ru/requirements/1/19).

### 4.3. Автоопределение языка

На старте прочитать `ysdk.environment.i18n.lang` и использовать его для выбора поддерживаемого языка. Это требуется даже для игры с одним языком. В черновике портала заявлять RU и EN; для `be`, `kk`, `uk`, `uz` применять RU, для остальных кодов — EN. Это соответствует [правилу автоопределения](https://yandex.ru/dev/games/doc/ru/requirements/2/14) и [резервному набору языков](https://yandex.ru/dev/games/doc/ru/concepts/languages-and-domains).

Реализован выбор RU/EN при инициализации SDK по `ysdk.environment.i18n.lang` с указанным резервным набором. До ответа SDK экран загрузки использует язык браузера; затем до показа выбора сохранения и меню обновляются язык документа, метаданные и тексты игры. Словарь EN покрывает интерфейс, названия и описания контента, подсказки, результаты и системные сообщения. Отдельно проверить через debug-панель Яндекса индикатор `I18N is used` и оба языка; перевод карточки игры в консоли площадки остаётся отдельным шагом.

### 4.4. Пауза SDK и разметка геймплея

Подписаться на `game_api_pause` и `game_api_resume`: стартовая реклама портала использует эти события и не имеет callback нашего рекламного вызова. Останавливать симуляцию и звук; возобновлять только после снятия всех причин паузы. [События SDK](https://yandex.ru/dev/games/doc/ru/sdk/sdk-events).

В `GameDirector` набор источников паузы сохранён; подключены независимые `platform` и `advertisement`, Gameplay API следует состоянию активного боя. Моки проверяют сохранение ручной паузы после resume SDK. Закрытие рекламы не должно снимать паузу, поставленную игроком.

Исправлено: `blur` в `mountGame.ts` останавливает симуляцию через отдельный источник `focus` и выключает звук; `focus` снимает только свою причину паузы.

Рекомендуем подключить `GameplayAPI.start()/stop()`: start при активном бое, stop при паузе, результате, меню, рекламе, скрытии вкладки. При наличии разметки её моменты обязаны соответствовать фактическому процессу. Для проекта простой источник истины — переходы условия `phase === 'battle' && !paused`, без повторного вызова каждый кадр. [Разметка геймплея](https://yandex.ru/dev/games/doc/ru/sdk/sdk-game-events).

### 4.5. Рекламные точки нашей игры: золото ×2 и темп боя ×2

**Статус: проектирование, код ещё не реализован.** Пользователь предложил обе точки 28.09.2026. Ниже зафиксированы предлагаемая трактовка награды, правила интерфейса и технические критерии; они заменяют прежнее предложение первого релиза только с interstitial.

Оба предложения используют **rewarded video — `ysdk.adv.showRewardedVideo()`**, а не обычный полноэкранный рекламный блок. Награда выдаётся через `onRewarded`; простое закрытие ролика не подтверждает её получение. Рекламу запускает явная кнопка, базовая игра доступна без просмотра. [SDK рекламы](https://yandex.ru/dev/games/doc/ru/sdk/sdk-adv), [требования к добровольным бонусам, пункты 4.5–4.7](https://yandex.ru/dev/games/doc/ru/concepts/requirements).

#### Карта размещения

| Момент | Предложение | Обычное действие | Ограничение |

| Поражение | Та же кнопка ×2, если G > 0 | Таланты, повтор боя | Удваивается реально заработанное золото |
| Активный бой, ручная пауза, таланты | Новых предложений нет | Обычные действия | Не прерывать найм/выбор |

В интерфейсе всегда видны обычное действие и добровольный бонус. Не превращать закрытие экрана, выбор карты усиления или кнопку начала боя в скрытый запрос рекламы. На экране результата кнопка ×2 находится рядом с итогом золота; на подготовке ускорение — рядом с запуском, без отдельного навязчивого окна.

#### А. Золото за бой ×2

**Предлагаемая трактовка «награды»: всё золото конкретного завершённого боя**, то есть `BattleReport.goldEarned`: убийства + завершённые игровые секунды + бонус победы, если она есть. Не удваивать весь кошелёк, очки глобальных талантов, открытия бойцов или выбранное усиление похода.

Базовое золото уже начисляется во время боя и остаётся после поражения. Поэтому успешный просмотр добавляет **ещё G**, а не выдаёт 2G заново и не умножает текущий баланс кошелька.

```text
G = зафиксированное goldEarned в результате завершённого боя
без рекламы: за этот бой начислено G
успешная реклама: дополнительное начисление G, суммарно 2G
```

Пример: в Каменном веке заработано 20 за убийства, 60 за игровые секунды и 25 за победу: G = 105. На результате: «Получено 105 золота» и «Реклама: золото ×2 · ещё +105». После просмотра: «За бой: 210 золота · бонус получен». Если игрок потратил часть золота на талант до просмотра, размер бонуса остаётся 105.

Предлагать после **каждого завершённого боя**, включая поражение и повтор ранее пройденного этапа. При поражении бонуса победы нет; при G = 0 рекламную кнопку не показывать. Возможность закончить без рекламы сохраняется всегда. Выбор карты усиления не требует просмотра.

При успешном просмотре сохранять бонус и признак получения вместе. Переход к следующему этапу закрывает возможность удвоить прежний результат. Просмотр должен оставить игрока на результате, чтобы тот сам выбрал усиление/повтор/переход.

**Экономический эффект:** для регулярно смотрящего рекламу игрока приток золота может приблизиться к удвоенному. Это ускоряет прокачку постоянных талантов и базы; баланс без рекламы обязан оставаться проходимым. Параметры бонуса победы 25/50 не меняются — рекламная прибавка учитывается отдельно. Измерять также повторные поражения: золотой бонус за них может стимулировать фарм, поэтому проверить реальные стратегии, а не заранее вводить штраф за проигрыш.

#### Б. Темп всего боя ×2

Это ускорение времени, **без преимущества одной из сторон**. Предлагать после выбора отряда на существующем экране подготовки, до вызова `beginBattle()`.

Кнопки:

```text
[Начать бой]
[Реклама: темп этого боя ×2]
Подсказка: обе армии, припасы и таймеры движутся вдвое быстрее.
```

Успешный просмотр разблокирует ×2 **для одной конкретной попытки** и возвращает на подготовку: «Темп ×2 доступен», основная кнопка становится «Начать бой ×2». Не начинать бой в callback автоматически — человек должен успеть вернуться к управлению. При ошибке или закрытии без награды обычный старт доступен при ×1.

Одинаково ускоряются перемещение, атаки, лечение, доход обеих сторон, решения противника, волны, таймер глифа, появление/защита босса и игровая длительность. Музыку и звуковысотность не ускорять; события звука следуют событиям боя. Меню и длительность рекламного ролика живут в обычном времени.

За те же **игровые** 60 секунд начисляется 60 золота времени; при ×2 они проходят примерно за 30 реальных секунд. Отдельного множителя золота, урона, HP, припасов или стоимости нет. При одинаковых действиях на тех же шагах симуляции исход и базовое золото должны совпадать. Доход золота в расчёте на реальную минуту при этом увеличится — это реальный эффект ускорения, который нужно учитывать при анализе экономики.

**Нюанс управления:** у живого игрока вдвое меньше времени на найм и реакцию. Поэтому это не обещание «бой станет легче» и не гарантированная победа. Предлагается после просмотра показывать компактный переключатель ×1/×2 в бою: вернуться к ×1 и снова включить ×2 можно бесплатно в пределах оплаченной просмотром попытки. Обычному игроку ×1 доступен без рекламы.

Право ускорения связывать с идентификатором попытки, сохранять при перезагрузке и снятии паузы. Текущее восстановление начинает тот же бой заново — ускорение сохраняется только для этой попытки, без нового просмотра и без переноса на другой этап. Явное «Повторить бой» после результата создаёт новую попытку с ×1; новая реклама предлагается добровольно. Перезапуск похода или переход к следующему бою также сбрасывает право. Не наследовать ×2 от глобального Debug-параметра.

Отображать ×2 в HUD и подписывать время результата как игровое. Рекорды времени сравнивать по времени симуляции; реальную длительность хранить отдельно для аналитики, иначе ускорение создаст несопоставимые рекорды.

**Выигрыш по времени не всегда положительный.** Пример оценки, не норматив: бой занимает 60 реальных секунд при ×1, при ×2 — около 30; рекламный ролик в 30 секунд съест всю экономию. Для длинных боёв польза заметнее. Нужно измерить длительность роликов и боёв; не обещать конкретное число сэкономленных секунд и не удлинять бой искусственно ради продажи ускорения.

#### В. Частота и сочетание рекламных точек

Предложения могут появляться на подготовке и результате каждого боя, но каждый просмотр выбирает сам игрок. В походе из четырёх боёв без повторных попыток максимум восемь успешных добровольных просмотров: четыре ускорения и четыре удвоения. При поражениях и повторах попыток их может быть больше. Не пытаться заполнить этот максимум автоматически.

Для первого релиза этой схемы **рекомендую отключить собственные обязательные межбоевые interstitial** и стики-баннеры. Два соседних добровольных просмотра уже могут приходиться на один переход: ×2 золото предыдущего боя, затем ×2 темп следующего. Не добавлять третий автоматический ролик. Стартовой рекламой портала управляет платформа; её паузы всё равно обрабатывать.

Если позже добавлять interstitial, отдельно оценить удержание и выбрать редкие естественные переходы без соседнего rewarded. Не запускать рекламу при получении результата до того, как человек успел увидеть награду, или сразу после отказа от добровольного бонуса. Это рекомендация UX для нашей игры, а не заявленный числовой лимит Яндекса. [Расположение рекламы](https://yandex.ru/dev/games/doc/ru/requirements/4/4).

#### Г. Технический контракт и защита от дублей

Расширить `YandexAdapter` методом rewarded с отдельными типами наград `battle-gold-double` / `battle-speed-double`. В нынешнем адаптере есть только interstitial, а `showIntermissionAd()` не вызывается из потока игры.

Предлагаемые правила реализации:

1. Один активный рекламный запрос на всю игру. Блокировать повторный запрос, начало/переход боя во время показа и гонку двух типов наград.
2. До показа зафиксировать цель: `attemptId`, эпоху, результат/подготовку и размер G. Не вычислять цель заново из текущего экрана в позднем callback.
3. Только `onRewarded` даёт право на бонус. `onClose` снимает рекламную паузу и закрывает запрос; без `onRewarded` бонус отсутствует. Если награда подтверждена, но закрытие/ошибка пришли позже, уже выданное не отменять и повторно не выдавать.
4. `rewardClaimId = attemptId + rewardType` — ключ однократной выдачи. Повторный callback, повторная загрузка результата или повтор синхронизации не дают второй бонус. `seed + battleIndex` недостаточно: настоящие повторы этапа могут использовать прежний seed.
5. Дельту золота и отметку выдачи хранить в одном снимке профиля либо применять через идемпотентную операцию с журналом. Раздельные записи «золото»/«получено» создают окно для дубля или потери при закрытии страницы. Для финальной победы и поражения результат/заявку хранить независимо от контрольной точки похода: текущая логика финала её удаляет.
6. При смене аккаунта или эпохи не отправлять награду в новый кошелёк. Проверять исходную цель запроса; предусмотреть восстановление уже подтверждённого незаписанного бонуса.
7. Базовую награду сохранять до рекламной попытки. Ошибка SDK, отсутствие сети или незасчитанный ролик не отнимают её и не блокируют продолжение.
8. Пересмотреть текущий watchdog 120 секунд: таймер не должен возвращать звук/бой поверх открытой рекламы. Все причины паузы должны сниматься независимо.
9. Повторить проверки с late callbacks, дублями `onRewarded`, порядком `onRewarded → onClose` и ошибкой после подтверждения. Не моделировать успех только фактом закрытия рекламы.

Собственный код не может гарантировать восстановление подтверждения просмотра, если вкладку уничтожили до получения/сохранения callback и платформа не предоставляет запись для восстановления. Сохранять подтверждённую награду сразу, а не ждать закрытия ролика; не обещать безусловный «exactly once» для всех аварийных ситуаций и двух одновременно изменяемых устройств без серверного решения.

#### Д. Применение ускорения в существующем коде

`src/main.ts` уже умножает накопитель симуляции на `battleSpeed`, сохраняя фиксированный шаг. Это подходящая основа для общего ×2. Но текущий `setBattleSpeed()` допускает ×1–×5, не ограничен попыткой и не сохраняет рекламное право. Нужен отдельный релизный контракт ×1/×2 с проверкой права, сбросом на новую попытку и восстановлением из профиля.

`BattleScene.ts` часть анимаций обновляет по реальному `delta`, часть привязывает к времени симуляции. Проверить ходьбу, атаку, поддержку, глиф, визуальные эффекты и HUD при ×2; иначе симуляция ускорится, а часть графики отстанет. На слабом устройстве ×2 требует примерно вдвое больше шагов в реальную секунду: профилировать длинные бои и большую армию. При перегрузке не пропускать обязательные шаги и не менять результат боя ради удержания частоты кадров.

Файлы для будущей реализации: `src/platform/yandex.ts`, `src/core/GameDirector.ts`, `src/core/save.ts`, `src/core/types.ts`, `src/main.ts`, `src/ui/GameUI.ts`, `src/view/mountGame.ts`, `src/view/BattleScene.ts` и связанные анимации. Формулы базового боя и `BattleSimulation.goldEarned` не требуют рекламного множителя.

#### Е. Приёмка рекламной схемы

- ×2 золото: обычная победа, финальная победа, поражение, G = 0, покупка таланта до просмотра, повтор этапа, восстановление результата.
- Одно успешное событие добавляет ровно G в исходную эпоху; повтор события/перезагрузка не добавляют золото снова.
- ×2 темп: обе армии и все игровые таймеры ускоряются; одинаковые команды по шагам дают тот же исход, время симуляции и золото.
- Бесплатное продолжение доступно при отказе, ошибке, отсутствии сети/SDK и незасчитанном просмотре.
- Переключатель ×1/×2, ручная и внешняя паузы, перезагрузка оплаченной попытки, сброс права на следующий бой/новую попытку.
- Конкурирующие запросы, поздние callbacks, смена аккаунта, закрытие приложения, облачная синхронизация.
- Полное прохождение без рекламы и с обоими бонусами: нет рекламного условия открытия эпохи, непроходимого боя или зависания перехода.

Рекомендуемые события аналитики: предложение, нажатие, открытие, подтверждение, закрытие, ошибка, выдача бонуса; привязывать к типу награды/эпохе/этапу/попытке. Для скорости сравнивать длительность боя отдельно от времени ролика; для золота — приток базовой валюты и рекламную прибавку, чтобы они не смешивались.

### 4.6. Сохранение и облако

Платформенное правило требует сохранения достижений и возможности продолжить после обновления/поворота, в том числе для гостя. Локальное хранение допускается без инап-покупок в подходящих простых играх; облако обязательно при покупках. [Сохранение прогресса](https://yandex.ru/dev/games/doc/ru/requirements/1/9).

Существующий проект предполагает облачный профиль, поэтому рекомендуемый первый выпуск включает:

1. `ysdk.getPlayer()` и чтение `player.getData()` до разрешения действий, меняющих профиль.
2. Версионированный профиль: эпохи/открытия, золото и таланты каждой эпохи, глобальные таланты/очки, рекорды, выбранная эпоха, контрольные точки.
3. Локальную резервную запись после значимых изменений; облачную очередь с ограничением частоты, повтором после ошибки и явным статусом синхронизации.
4. `setData(..., true)` в важных безопасных точках; учитывать, что обычная очередь ещё не означает подтверждённую запись на сервере.
5. Сохранение гостя без обязательного входа. Авторизацию предлагать отдельным осознанным действием с понятной выгодой.

Лимиты SDK: профиль `setData` — 200 КБ; `getPlayer` — 20 запросов/5 минут; `getData` и `setData` — по 100/5 минут; числовые stats — 10 КБ, методы stats — 60/минуту. Нельзя отправлять облачный запрос на каждую секунду начисления золота. [Данные игрока](https://yandex.ru/dev/games/doc/ru/sdk/sdk-player).

**Наше предложение разрешения конфликтов:** не складывать два кошелька и не выбирать максимум каждого поля. Валюта и купленные таланты должны переноситься согласованным снимком. Добавить версию/ревизию, идентификатор профиля и миграции; при двух независимо изменённых сохранениях выбирать целый профиль по определённой политике или предлагать понятный выбор между ними. Один `updatedAt` на клиентских часах не решает все конфликты.

Локальный прогресс с localhost или прежнего домена не попадёт в origin Яндекса автоматически. Для переноса существующих тестовых профилей понадобится явный экспорт/импорт либо отдельная миграция. Debug-настройки в облачный публичный профиль не переносить.

Текущее поведение обновления в бою: этап запускается заново, уже заработанное золото остаётся. Описать это в комментарии модерации и проверить на устройствах. Отдельно проверить экономический эффект повторных перезагрузок: не ломает ли повторный заработок золота темп прокачки.

### 4.7. Подготовить публичную сборку

**По указанию пользователя Debug пока не трогать. Панель, команды, локальный баланс и лаборатория сохранены в текущей сборке.** Первые четыре пункта ниже — отложенные рекомендации для будущего публичного состава, а не выполненные изменения и не требование площадки удалить инструмент с конкретным названием:

- Убрать Debug, редактор вражеского баланса и прямой выбор любого боя из публичного интерфейса.
- В релизе игнорировать локальные Debug-правки, чтобы профиль тестировщика не менял базовый баланс.
- Оставить один игровой entrypoint Vite; лабораторию сохранить для разработки.
- Не включать `sprite-lab.html`, старый preview, контактные листы и ресурсы только лаборатории в загружаемый пакет.
- Сделано `base: './'`; игровой build/preview проходит. Проверить пути в настоящем черновике. `/sdk.js` оставлен официальным платформенным путём.
- Сделано: метаданные обещают боссов двух реализованных эпох.
- Сделано: текущий прогон 117/117, основные документы обновлены; исторические записи остаются историей.

Удалять лишь подтверждённо неиспользуемые ресурсы. Vite копирует `public/` целиком; удаление дополнительного HTML-entrypoint само по себе не очищает эту папку.

### 6.2. Создание ZIP с проверкой структуры и размера

Текущая команда для Windows: `npm run package:yandex`. Результат — `artifacts/znamyona-epoh-yandex.zip`, сборка — `dist-yandex/`. Для локального просмотра этой сборки: `npm run preview:yandex`, затем открыть адрес Vite. Ниже исторический ручной пример; `dist/` теперь предназначен для разработки и содержит лабораторию.

Этот пример требует Python 3 и выполняется из корня проекта. Папка `release-artifacts/` предложена для результатов упаковки; добавить её в `.gitignore`, если не планируется хранить архивы в Git. Не размещать архив внутри `dist/`.

```sh
python3 - <<'PY'
from pathlib import Path
import hashlib
import zipfile

root = Path('dist')
assert (root / 'index.html').is_file(), 'Нет dist/index.html'
files = sorted(p for p in root.rglob('*') if p.is_file())
assert files, 'Сборка пуста'
size = sum(p.stat().st_size for p in files)
assert size <= 100_000_000, f'Сборка превышает 100 МБ: {size}'
for p in root.rglob('*'):
    name = p.relative_to(root).as_posix()
    assert not any(c.isspace() for c in name), f'Пробел: {name}'
    assert not any('\u0400' <= c <= '\u04ff' for c in name), f'Кириллица: {name}'
for p in files:
    assert p.name not in {'.DS_Store', 'Thumbs.db'}, f'Служебный файл: {p}'
assert not (root / 'sprite-lab.html').exists(), 'Лаборатория осталась в релизе'
assert not (root / 'sprite-preview.html').exists(), 'Preview остался в релизе'

out = Path('release-artifacts')
out.mkdir(exist_ok=True)
archive = out / 'znamyona-epoh-1.0.0.zip'
assert not archive.exists(), 'Архив уже есть: смените версию или сохраните прежний отдельно'
with zipfile.ZipFile(archive, 'w', zipfile.ZIP_DEFLATED) as z:
    for p in files:
        z.write(p, p.relative_to(root).as_posix())
with zipfile.ZipFile(archive) as z:
    assert z.testzip() is None, 'Повреждён ZIP'
    assert z.namelist().count('index.html') == 1
    assert sum(i.file_size for i in z.infolist()) == size
print('Unpacked bytes:', size)
print('ZIP bytes:', archive.stat().st_size)
print('SHA256:', hashlib.sha256(archive.read_bytes()).hexdigest())
print('Archive:', archive.resolve())
PY
```

Контрольные суммы/номер коммита записать в журнал релиза. После упаковки распаковать архив в новую папку вне сборки и проверить именно эти файлы через HTTP-сервер. Это ловит потерянные ресурсы и лишнюю внешнюю директорию. Затем загрузить **тот же ZIP** в черновик.

7. Открыть черновик и выполнить раздел 8 именно на загруженном архиве. Исправления требуют пересборки и повторной загрузки.
8. Проверить обязательные поля и договор, отправить заявку на модерацию. Записать версию ZIP, дату, SHA256 и коммит.
9. Следить за замечаниями в Консоли и почте. При отказе воспроизвести на указанном окружении, исправить и повторить всю связанную приёмку.
10. После одобрения: без отсрочки игра публикуется автоматически; с отсрочкой использовать кнопку публикации, затем проверить публичный запуск и рекламу.

Основание процедуры: [загрузка](https://yandex.ru/dev/games/doc/ru/console/add-new-game), [модерация](https://yandex.ru/dev/games/doc/ru/concepts/moderation).

Целевой срок полной модерации — 3–5 рабочих дней, контентной — 1–2; документация предупреждает о временно увеличенных сроках. Это не обещание даты релиза. Проверку могут остановить на первом нарушении, поэтому список замечаний бывает неполным.

После отклонений задержка повторной отправки растёт: 24 часа, 2, 4, 8, затем до 16 дней. В Консоли описан сброс ожидания не чаще одного раза за 28 дней. Не использовать модерацию вместо собственной проверки. [Процесс и повторная отправка](https://yandex.ru/dev/games/doc/ru/concepts/moderation).

## 10. Обновления и работа после релиза

Предлагаемый порядок проекта:

- Первые дни проверить публичную версию на устройствах, отзывы, запуск, рекламу и сохранение.
- Измерять старт похода, начало/результат каждого боя, повтор, открытие эпохи, покупку талантов; выбрать инструмент аналитики отдельно. Пользовательская аналитика не является найденным обязательным условием допуска.
- Контролировать сложность и отказы после поражения, состояние рейтинга, среднюю сессию и долю дошедших до Бронзового века.
- Исправления выпускать в **той же карточке**, повышая версию и сохраняя обратную совместимость профилей.
- Перед новым архивом сохранять прежний ZIP, материалы, версию схемы сохранений и журнал изменений. Проверить восстановление старого профиля в новой версии.
- Новые эпохи добавлять как обновления после отдельной проверки контента/баланса/ресурсов. Не создавать новую карточку для того же проекта ради повторной публикации.
- После смены файлов игры планировать повторную полную модерацию. Смена одних материалов также проходит соответствующую проверку.
- Следить за обновлениями правил и подсказками Консоли; перед каждым выпуском перепроверять источники этого документа.

Откат не считать мгновенным переключателем: держать прежний архив, но процедуру и сроки возврата проверять в Консоли. Старый код должен уметь безопасно работать с профилями новой версии либо иметь предусмотренный план миграции.

Браузерный smoke текущего build в Chrome с моками SDK: семь размеров без прокрутки, загрузка ресурсов, Game Ready, RU fallback, Gameplay API, SDK/ручная паузы и отмена контекстного меню проходят. Debug сохранён. Это не приёмка физического устройства или настоящего SDK. Тесты симуляции допускают накопление золота и повторы поражений; темп прокачки ещё требует ручного плейтеста.

## 11. Очередь задач и финальный чеклист

### Порядок подготовки

| Очередь | Задача | Критерий готовности |
| --- | --- | --- |
| 1 | Аккаунт/договор/выплаты | Доступен путь публикации для реального владельца |
| 2 | Контентный аудит | Проверены спорные названия, символика, рейтинг, права |
| 3 | SDK + язык + ready + паузы | Пройдены индикаторы и сценарии в черновике |
| 4 | Сохранения | Нет потерь/дублей; выбран и проверен локальный/облачный вариант |
| 5 | Rewarded: золото ×2 / темп ×2 | Оба бонуса однократны, отказ и ошибки не мешают игре |
| 6 | Публичная сборка (отложена) | Debug пока сохранён по указанию пользователя; отдельно подготовить итоговый состав и ZIP перед отправкой |
| 7 | Прогрессия и UI | Обновлённые тесты и ручное прохождение на устройствах |
| 8 | Материалы | Иконка, обложка, видео, скриншоты и тексты валидны |
| 9 | Модерация/выпуск | Проверен финальный черновик, получено одобрение |

### Перед отправкой

- [ ] Договор заключён, профиль и контактная почта корректны.
- [ ] SDK загружается по официальному пути и реально инициализируется.
- [ ] Game Ready привязан к готовности; язык SDK определён на старте.
- [ ] Паузы SDK/рекламы/visibility/фокуса/игрока не конфликтуют.
- [ ] Гостевой прогресс сохраняется; облако и миграции проверены, если заявлены.
- [ ] Rewarded включена на подготовке/результате; золото ×2 и право темпа ×2 проверены, нет дублей и зависания при пропуске/ошибке.
- [ ] Принят публичный контент, рейтинг и права на материалы.
- [ ] Полный прогон тестов и ручная прогрессия проверены; известные ошибки устранены или объяснены до релиза.
- [ ] Подготовлен согласованный публичный состав; сейчас Debug и лаборатория намеренно сохранены, задача отложена.
- [ ] Распакованный ZIP ≤100 МБ, `index.html` в корне, допустимые имена.
- [ ] Тестировался тот же архив, который отправляется.
- [ ] Заявлены только проверенные устройства, ориентации и языки.
- [ ] Заполнены поля, загружены обязательные изображения/ролик/скриншоты.
- [ ] В карточке и комментарии нет обещаний ещё не реализованных возможностей.
- [ ] Сохранены ZIP, SHA256, коммит, версия профиля и результаты приёмки.
